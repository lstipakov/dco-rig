Ioctl

Fuzzing the API

Every ioctl, called with mutated buffers — in multipeer mode, then again point-to-point, where the multipeer half should be refused — plus control codes the driver does not implement. Three things get mutated:

Buffer shapes

Input truncated to one byte and to one short of the struct, oversized, absent. Output too small, absent. Two past findings lived here, so it runs against every ioctl.

Values

Peer ids at the ends of the range, key lengths that are not 16, 24 or 32, enums past their last member, prefix lengths past 32 and 128, and the sockaddr families that decide how far the driver reads.

Pointers

Null with a non-zero length, and lengths that would overflow a size calculation.

Nothing asserts on the status a call returns. A refusal is the right answer to most of this and the driver may choose which refusal, so the run only calls out what should never have been accepted at all — a buffer shorter than the struct the driver reads, or a value outside its documented range. Driver Verifier judges the rest.

Ioctl

Racing the API

Ids come from a deliberately small space, so they are reused constantly, and one thread installs keys on the ids another is deleting.

On the control channel a reader finds the queue empty and parks, while the receive side takes the same lock to decide whether to hand it a packet or queue one. That window is the bug. So control traffic is deliberately rare — one datagram in 256. Flood it and the queue is never empty, the reader always finds a packet waiting, never parks, and never races.

Stress

Testing iroutes

A peer's own address is in the peer table; subnets reachable behind a peer are in a trie, consulted only when that table misses. Peer churn rewrites the trie thousands of times a run, and traffic between tunnel addresses never once reads it — so the probes have to manufacture the lookups.

Every client is handed the same iroute, 10.90.0.0/24, so the prefix always has an owner and ownership moves every time anyone connects. Addressing that subnet rather than a tunnel address is what pushes a lookup past the peer table. It happens on two paths:

1  the server pings into the subnet

send path · destination lookup

A destination no peer holds as its own address. The trie resolves the prefix to its owner, which does hold it and answers. The reply proves the trie routed out.

2  a client pings from inside it

receive path · source lookup

Reverse-path filtering checks the source against the sending peer, misses, falls to the trie. Only the real owner is answered, so a reply proves the trie validated a source coming in — and names the owner.

3  everyone pings an address nobody holds

send path again · 100/s · all run

No table can ever answer it, so every packet reaches the trie — and nothing replies, because the owner is usually a dev null client. It asserts nothing. It re-runs probe 1 while churn rewrites the structure underneath.

Probes 1 and 2 run before the swarm and the flood begin, and that ordering matters: later the owner is usually a flood client with no interface at all, which would resolve and deliver correctly and still never answer.

What it has caught

ioctl

Write-path self-send deadlock — present since 2.4.0

Needs a control write addressed to the driver's own endpoint while another writer is queued. An ordering OpenVPN never produces.

CVE-2026-105390·fix #162
stress

A timer holding a freed peer

The window is microseconds. The swarm kills clients with pings still in flight — exactly when the driver frees a peer and detaches its timer.

report #141·fix #146
ioctl

A lost wakeup on the control read path

A reader parks, a packet arrives, both take the same lock. It needs a reader that actually has to park — a flood would just leave a backlog and race nothing.

report #136·fix #138

Correctness tests pass: the handshake completes. Only the clock shows it.

ChaCha20 is slow on Windows

CNG's ChaCha20-Poly1305 is scalar and bound per byte. On one core AES-256-GCM runs 25× faster, because AES-NI does it in hardware. That is fine while AES is the default — but anyone who configures ChaCha pays for it.

Case study · what it cost

Then it bugchecked the machine

Two gigabytes into a run, the box died — in unrelated code, with ovpn_dco nowhere on the stack. poly1305's VPMADD52 path ends in vzeroall, which zeroes ymm0–15. On Win64 the low halves of XMM6–15 are the caller's to keep, and MSVC had live values in them.

The fix is one word — vzeroall to vzeroupper — after which 50.6 GB went through clean at 7.24 Gbit/s with the fast path still live. Nothing cheaper would have found it.

filed: dot-asm/cryptogams #20·openssl #12744·openssl #21522·openssl fix #21808

OpenSSL knew: #12744 reported exactly this in 2020, #21522 the same for the 8x path, and #21808 fixed both by excluding VPMADD52 on Win64 outright. dot-asm's tree — the BSD-licensed one a GPLv2 driver can actually use — still ships it unguarded.

Where it's thin

  • One architecture. Everything is x86-64. ARM64 builds in CI, never runs on hardware.
  • Short runs. 15 s per direction catches collapses, not slow leaks.
  • Throughput only. No latency, no jitter, no loss behaviour.
  • The network caps half of it. Several results sit on a per-flow ceiling near 7.4 Gbit/s.
  • CI figures aren't absolutes. On one build CI reported 5.89 Gbit/s for the Windows server's send direction, where a hand-run interleaved measurement of that same build gave 7.41. Unexplained.
